## Что делает сценарий

1. Поднимает три сервера. Сохраняет конфигурации, myid, роли и вывод версий.
2. Останавливает zk3, затем zk2. Проверяет реальную запись через клиента: при двух работающих серверах запись проходит, при одном соединение/запись недоступны. Сохраняет `srvr`, затем восстанавливает серверы.
3. Через настоящий zkCli создаёт эфемерный узел, читает его и завершает сессию командой `quit`. Во второй сессии проверяет отсутствие узла. Это корректное закрытие сессии; при аварийном закрытии исчезновение происходит после истечения тайм-аута.
4. Скачивает исходные вакансии из RustFS. Запускает координатор a и ждёт первый сохранённый чекпоинт. Запускает b, замораживает весь контейнер a через `docker pause`, включая heartbeat ZooKeeper. Ожидает завершение b и не менее 40 секунд паузы, затем возобновляет a.
5. Повторяет эксперимент с защитой публикации. Проверяет количество записей, версию указателя, владельца результата, восстановление с ненулевого чекпоинта и совпадение с ДЗ 3. Записывает фактическую длительность смены лидера.

При ошибке не публиковать работу как выполненную: сохранить вывод и исправить причину. Скрипт не удаляет старые запуски. Идентификаторы прогонов содержат время. Контейнеры координаторов сохраняются для диагностики. `docker compose down` останавливает серверы, сохраняя тома; не запускать во время расчёта.

## Устройство решения

Три сервера имеют отдельные Docker-тома данных и журналов. Внутри контейнеров порт 2181 одинаковый благодаря отдельным сетевым пространствам; на Windows порты 2181, 2182, 2183. Docker entrypoint создаёт zoo.cfg и myid из переменных compose.

Не путать лидера ансамбля ZooKeeper с лидером расчёта. Замораживается координатор a, а не один из серверов ZooKeeper.

Координаторы используют Kazoo, тайм-аут сессии 10 секунд. Захват эфемерного `/leader` и увеличение версии `/epoch` выполняются одной ZooKeeper-транзакцией. Версия `/epoch` служит fencing token. После истечения сессии a узел `/leader` исчезает, b получает новую эпоху и продолжает с чекпоинта.

Исходный CSV читается потоково. При восстановлении строки до сохранённой позиции пропускаются, а счётчики восстанавливаются из чекпоинта, поэтому вклад старых строк не суммируется второй раз. Для воспроизводимой паузы после каждого блока 10 000 строк добавлена задержка 1 секунда. Это искусственное замедление вычисления, не подмена результата.

Используются исходные функции `parse_skills` и `table_bytes` из `../devops-lab/mapreduce.py`. Расчёт выполняется заново по исходным вакансиям, а не по готовому pairs.csv. Сравниваются числа, SHA-256 и все байты CSV с результатом ДЗ 3.

Чекпоинты и кандидаты результата записываются под уникальными именами. Текущими считаются только файлы, на которые указывают узлы `/checkpoint` и `/result`. Устаревший лидер не может изменить указатель чекпоинта даже в эксперименте без защиты результата.

В режиме `FENCING=0` публикация — безусловный `set` узла `/result`: b записывает версию 1, a после возобновления перезаписывает её до версии 2.

В режиме `FENCING=1` проверка версии `/epoch` и изменение `/result` выполняются **одной атомарной multi-транзакцией**. Устаревшая эпоха даёт `BadVersionError`. Отдельная проверка эпохи перед внешней записью была бы недостаточна: между проверкой и записью может смениться лидер.

В данной реализации получателем публикации является сам ZooKeeper, хранящий указатель. Поэтому он и проверяет эпоху при изменении указателя. Файлы кандидатов неизменяемые; наличие двух файлов не означает две принятые публикации. Для изменяемой внешней базы или S3-объекта нужен контроль эпохи на стороне соответствующего получателя: ZooKeeper сам не блокирует внешние записи.

Общий каталог Docker имитирует общее хранилище одного компьютера. Демонстрируется отказ процесса координатора и потеря кворума; отказ всего Windows-компьютера этим стендом не покрывается.

## Доказательства и отчёт

В `logs` сохраняются реальные JSONL-журналы координаторов, вывод команд, конфигурации, серверные журналы, проверенные CSV и `*-summary.json`. Поле `failover_seconds` измеряется от успешного завершения `docker pause` до события LEADER у b. Время выполнения самой команды вынесено в `pause_command_seconds`; точный момент заморозки лежит между её началом и завершением.
